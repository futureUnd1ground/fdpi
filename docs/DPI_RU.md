# ╭─ DPI: как устроен анализ и обход ─╮

DPI — Deep Packet Inspection, анализ сетевых пакетов и их связи с потоком.
Оборудование может классифицировать протоколы, применять политики доступа,
блокировать соединения или ограничивать скорость. Сама технология применяется
и в обычных системах безопасности, и в системах фильтрации.

## Что видно в сети

| Уровень | Доступная информация | Граница возможностей |
|---|---|---|
| IP и транспорт | Адреса, порты, направление, размеры и интервалы пакетов | Один IP может обслуживать множество сайтов |
| Открытый HTTP | Метод, Host, заголовки и незашифрованное содержимое | Для HTTPS содержимое защищает TLS |
| Начало TLS | Параметры ClientHello, обычно SNI, если имя не защищено отдельно | Это не доступ к содержимому HTTPS после установления TLS |
| Поток | Последовательность пакетов и повторные передачи | Сложность анализа зависит от реализации и ресурсов |

SNI позволяет клиенту указать имя сервера при установлении TLS; одно только
использование HTTPS не означает, что это имя скрыто. Расширение описано в
[RFC 6066, раздел 3](https://www.rfc-editor.org/rfc/rfc6066.html#section-3).

TLS защищает прикладные данные от прослушивания и подмены. Устройство на
маршруте не получает возможность читать пароли и страницы лишь потому, что
оно называется DPI. Перехват с доверенным клиенту сертификатом — отдельная
ситуация. См. [TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446.html).

## Почему важна сборка потока

Сообщение приложения и TCP-пакет — разные единицы. Один TLS ClientHello может
занимать несколько сегментов. Чтобы надёжно распознать его, анализатору нужно
учесть порядок, номера последовательности и повторные передачи.

```text
Приложение:   [          TLS ClientHello          ]
TCP:          [ часть A ] [ часть B ] [ часть C   ]
Сервер:       [          собранное сообщение      ]
DPI:          сборка потока + распознавание + политика
```

Если анализатор и конечный сервер по-разному интерпретируют поток, возникает
возможность рассинхронизации. Стратегия пытается использовать конкретное
различие. Полноценная сборка потока на стороне DPI может лишить простой
приём эффективности. Разделить сообщение на части не означает зашифровать его.

## Что делают стратегии FDPI

| Приём | Смысл | Ограничение |
|---|---|---|
| `multisplit` | Разделяет исходные TCP-данные в заданных позициях | DPI может собрать данные заново |
| `multidisorder` | Меняет порядок отправки частей | TCP на сервере должен восстановить исходный поток |
| `fake` | Добавляет ложные пакеты с параметрами, при которых сервер должен их отвергнуть | Нельзя считать, что любой DPI обязательно примет такой пакет |
| Фиксированный TTL | Ограничивает дальность прохождения ложного пакета | Нужное значение зависит от маршрута |
| HTTP Host case | Меняет регистр имени заголовка в открытом HTTP | Не меняет зашифрованные заголовки HTTPS |
| QUIC fake | Воздействует на начальные QUIC-пакеты | Не заменяет собой обработку TCP/TLS |

Это описание модели FDPI. Реальную обработку выполняют внешний nfqws2 и его
Lua-функции, а Go-код FDPI проверяет конфигурацию и управляет их запуском.
Параметры и привязка к версии движка — в [ENGINE.md](ENGINE.md).

## Почему QUIC проверяется отдельно

QUIC использует UDP и интегрирует TLS. Защита Initial-пакетов не даёт тех же
гарантий конфиденциальности, что защита прикладного трафика: начальные ключи
выводятся из общедоступных параметров соединения. Поэтому наличие шифрования
QUIC само по себе не исключает анализ начального обмена.
См. [RFC 9001, раздел 5.2](https://www.rfc-editor.org/rfc/rfc9001.html#section-5.2).

Успешный запрос по HTTP/2 через TCP не подтверждает работу HTTP/3 через QUIC.
Браузер также может выбрать другой транспорт, чем диагностическая команда.

## Как устроен путь пакета в FDPI

```text
Приложение → nftables → NFQUEUE 24000 → nfqws2 → сетевой интерфейс
                          ↑                │
                          ╰─ решение о пакете
```

1. Правила ограничивают перехват начальными исходящими пакетами на выбранных портах.
2. Движок сопоставляет распознанный HTTP Host, TLS SNI или QUIC с доменным профилем.
3. Выбранные преобразования применяются только к подходящему трафику.
4. Сгенерированные пакеты имеют mark, исключающий повторную обработку самим FDPI.

Именно поэтому профиль домена не равен фильтру процесса. Два приложения,
обращающиеся к одному домену, могут попасть под один профиль. Зашифрованное
или нераспознанное имя может сделать доменное сопоставление невозможным.

`queue bypass` пропускает пакеты без слушателя очереди. Он не исправляет
неподходящую стратегию при работающем движке. Супервизор удаляет свою таблицу
при штатной остановке и обнаруженной аварии; чужие таблицы сохраняются.

## Где анти-DPI не поможет

- Запрет по IP до анализа протокола может не зависеть от формы ClientHello.
- Ошибку DNS нужно отличать от остановки соединения после TLS-запроса.
- Запрет по стране, аккаунту или подписке может исходить от самого сервиса.
- Неверный маршрут, MTU или kill switch VPN могут блокировать рабочую стратегию.
- Закрытый порт и недоступный сервер не становятся доступными от сегментации.

FDPI не создаёт VPN-туннель, не переносит выход в другую страну и не обещает
скрыть IP клиента. Сертификаты TLS по-прежнему должны проверяться приложением.

## Как проверять результат

```text
DNS → TCP → TLS → HTTP → API приложения → медиаданные → воспроизведение
```

Проверяйте этапы отдельно. Загруженная оболочка YouTube может сосуществовать
с недоступным API главной. HTTP 200 может содержать заглушку; HTTP 403 —
доказывать ответ сервера, но не доступ к функции приложения.

```bash
fdpi doctor
fdpi test www.youtube.com
fdpi test-service youtube
fdpi lab youtube
```

Для сравнения стратегий нужен одинаковый маршрут и отсутствие незаметного
перехода в VPN. В отчёте сохраняйте локальный адрес, коды HTTP, тип и объём
данных, а также неудачную базовую проверку без целевой стратегии. Один скачанный
диапазон видео подтверждает передачу этого диапазона, но не непрерывное
воспроизведение, звук или работу личного аккаунта.
